# Sources recovered from the 2026-11-15 build

The repository stopped at commit `3a493ff` (2026-10-11), but `S4OM.ts4script` kept shipping.
This branch holds source recovered from the build dated 2026-11-15, so the repository and the
shipped mod describe the same code again.

## What this is

- `src/multimod/` — 44 modules. 16 existed here before and are updated; 28 are new.
- `src/ctypes/` — the four pure-Python `ctypes` files the build bundles. They are the unmodified
  CPython 3.7.9 standard library files (the game ships `_ctypes` but not the Python half).

The package is plain Python 3.7 bytecode with no obfuscation, so the source was recovered by
decompiling and then checking the result against the original, function by function.

## How far it can be trusted

Every recovered file was compiled with Python 3.7 and compared with the shipped `.pyc`:
bytecode, constants, names, variables, argument counts and flags of every code object.

| | code objects | identical to the shipped build |
|---|---|---|
| `multimod` (44 modules) | 966 | 966 |
| `ctypes` (4 modules) | 95 | 95 |

A package rebuilt with `build.py` from this branch has the same 48 entries as the shipped one and
identical bytecode in each (file names and line numbers aside).

So the *behaviour* is exactly the shipped build's. What is not original:

- **Comments.** Bytecode has none. Where a function is unchanged since `3a493ff` its old text is
  kept, comments included. Changed and new functions have docstrings only.
- **Formatting and exact wording** of changed and new code. `if a and b:` and nested `if a: if b:`
  compile to the same thing; the recovered text picks one. The 28 new modules were run through
  `black` (line length 110) for readability.
- **Local structure that leaves no trace**, such as blank lines and the order of `global`
  statements.

Decompiler output alone was not enough: the better of the two decompilers got about two thirds
of the code objects right (they drop comprehension filters, mis-nest `if`/`elif` chains and
mangle some slices). Picking, per function, whichever of the two decompilers or the old source
matched reached 859 of 966; the remaining 107 were corrected by hand against the disassembly.
`network._process_incoming` could not be decompiled at all and was rebuilt from its disassembly
on top of the old text. All of it is covered by the comparison above.

## Changed modules

`git diff main -- src/multimod` shows the detail. Largest changes: `network` (new message types,
outbound queues per connection, relay error messages, notification queue), `lobby` (game-version
check in the handshake, received saves never overwrite a player's own save), `buy_sync` (objects
bought and deleted, not only moved), `interaction_sync` (crafting and cooking, retries),
`sync` (walk destinations, the host's other Sims, seated Sims). `clock_sync`, `core_hooks`,
`event_system`, `local_ops_filter` and `stats_sync` are nearly unchanged.

Much of that diff is formatting rather than behaviour: a changed function is shown in the
decompiler's style, so its old comments appear as removed.

## Protocol changes since `3a493ff`

`docs/PROTOCOL.md` does not cover these yet.

- `hello` and `welcome` carry `game` (the sender's Sims 4 build); a mismatch produces a notice.
- The host re-broadcasts these from one joiner to the others (`PEER_RELAY_TYPES`): `sim_pos`,
  `mood`, `interaction`, `inventory`, `relationship`, `object_pos`, `object_new`, `object_del`,
  `stats_sync`, `money_sync`, `sim_state`, `event_start`, `event_end`, `sim_look`,
  `object_state`, `activity`, `build_lock`, `player_left_lot`.
- New message types handled by `network._process_incoming`:

| type | handler |
|---|---|
| `byos_import`, `world_move`, `control_rules` (host only) | `byos`, `living_world`, `control` |
| `dialog_fwd`, `dialog_answer`, `sim_owners` | `dialog_router` |
| `start_hold` | `start_hold` |
| `lot_live`, `lot_live_failed` | `lot_live` |
| `npc_req`, `npc_data` | `npc_sync` |
| `activity`, `object_state`, `sim_look`, `sim_state` | `activity_sync`, `object_state_sync`, `look_sync`, `sim_state_sync` |
| `world_state`, `world_req`, `event_start`, `event_end` | `world_sync` |
| `object_new`, `object_del` | `buy_sync` |
| `host_left`, `host_back`, `player_left_lot` | `world_flow` |
| `build_lock` | `lot_share` |
| `resync_start`, `resync_ready`, `resync_failed` | `resync` |
| `challenge_start`, `challenge_update`, `challenge_end`, `challenge_progress` | `party_games` |
| `state_check`, `obj_list`, `obj_list_req` | `desync_repair` |

- `world_snapshot` may carry `challenge` (a party game in progress when someone joins).
